# Bridge Wonder V29 — 로그인·관리자 5단계 가속

2026-11-20 기준. 기존 브릿지 원더의 크림·포레스트 그린 테마, 학생/급여 자료, 서버 직원별 권한을 유지합니다.

## 1단계: 초기 화면과 정적 파일
- Google 외부 iframe 없이 GitHub 자체 도메인에서 로그인 화면을 즉시 표시합니다(기존 V28 구조 유지).
- 업무용 CSS 사전 로딩과 Google HTTP 연결 힌트 추가.
- 비밀번호 네이티브 검증 모듈은 본문 앱보다 먼저 로딩. 기존 관리자 JS의 로딩 순서와 디자인은 유지.
- 기존 급여 JS/CSS는 로그인 시작 때 불러오지 않습니다.

## 2단계: 비밀번호 인증 병목 해소
기존 Google Apps Script 코드의 PBKDF2-HMAC-SHA256 24,000회 반복 연산은 Google 실행 환경에서 로그인 지연의 원인이 될 수 있습니다. 실제 Google 응답시간은 운영 계정에서 측정해야 합니다.

- 새 입력/로그인은 브라우저의 **Web Crypto PBKDF2-HMAC-SHA256 (160,000회)**를 사용해 256비트 검증값을 만듭니다.
- Google은 이 검증값을 비공개 pepper로 다시 HMAC-SHA256 처리해 저장/검증합니다. GitHub에는 서버 pepper를 보관하지 않습니다.
- 기존 V1 비밀번호를 가진 계정은 **처음 한 번 기존 비밀번호를 정상 확인한 뒤** V2 검증 기록으로 전환합니다. 첫 전환 로그인은 여전히 느릴 수 있습니다.
- 구버전 Google HtmlService 클라이언트는 기존 V1 verifier를 이용해 로그인할 수 있도록 보존합니다. 구버전 방식은 느리지만 서버 권한 검사를 우회하지 않습니다.
- OTP 비밀번호 최초 설정/재설정도 브라우저 native PBKDF2 proof를 지원합니다.
- 브라우저의 WebCrypto를 사용할 수 없는 경우 신규 버전에서도 기존 서버 검증 경로를 이용합니다.
- **중요**: 브라우저 PBKDF2 proof는 비밀번호에 준하는 비밀값입니다. 이를 서버 로그·브라우저 저장소·URL 등에 기록하지 않습니다. 현재 로그인 API는 기존과 같이 TLS로 비밀번호도 전송합니다.

## 3단계: HTTP 및 시간 초과 처리
- 기존 Google 전용 HTTP ContentService 구조 유지. Cloudflare/외부 API 없음.
- 로그인과 최초 등록의 자동 응답 대기 한도를 네트워크 85초·관리자 호출 90초로 일치시키고, 10초 이상 지연 시 최초 전환 안내를 표시합니다.
- 저장·급여 확정 요청은 자동 재시도하지 않아 중복 저장을 방지합니다.
- **HTTP method 명칭과 요청 소요시간만** 최근 30건을 메모리에 기록합니다. 비밀번호, 검증값, 세션 토큰, 이름 등은 기록하지 않습니다.
- Chrome 콘솔에서 `BW27Bridge.metrics()`로 HTTP 처리 시간, `BW29LastLoginTiming`으로 브라우저 PBKDF2와 Google 인증 시간을 별도 확인할 수 있습니다.

## 4단계: 업무 데이터 및 화면
- 기존 V28.2의 정적 대시보드 선표시, 운영 통계 비동기 조회, 메뉴 렌더링 최적화, 캐시 정책, 최대 4개 실제 읽기 동시 실행을 유지합니다.
- 원장 로그인 후 브라우저가 한가해졌을 때만 급여 화면 CSS/JS를 사전 로딩합니다. **급여 내역을 사전 조회하거나 저장하지는 않습니다.** 절전/2G 연결에서는 생략합니다.
- UI 버전과 Google HtmlService 관리용 생성 파일 버전 29로 맞추고 빌드 스크립트도 동일하게 변경합니다.

## 5단계: 검증 및 배포
- `npm run check`는 JavaScript/JSON/HTML, 전체 로컬 참조, 기존 테마 보존, Google UI 생성 파일의 소스 일치를 검사합니다.
- `npm test`는 기존 급여·출결·권한·서류·HTTP/가속 회귀검사와 V29 네이티브 암호화, 기존 비밀번호 자동 이전, 잘못된 비밀번호/락아웃, 비공개 급여 조건을 검사합니다.
- 160,000회 native PBKDF2는 로컬 Node 시험에서 수십 ms였으나 이는 실제 운영 Chrome·Google 측의 응답 시간 측정이 아닙니다.
- 운영 Google 프로젝트에 파일이 배포되기 **전에는** V29 로그인의 server fast path가 동작하지 않습니다. GitHub 변경과 Apps Script 배포는 별도입니다.

### Google 적용 순서
1. 기존 Staff Administration 프로젝트의 `Code.gs`, `Admin.html`, 프로젝트 속성, Google Sheets를 백업합니다.
2. GitHub `server/apps-script/Code.gs` **전체 파일**을 기존 직원 프로젝트 `Code.gs`에 교체합니다.
3. Google 직접 접속 경로를 계속 사용한다면 `server/apps-script/Admin.html`도 교체합니다. `Payroll.gs`, `StaffBridge.gs`는 기존 V27 파일을 그대로 둡니다.
4. 기존 배포 관리 → 배포 수정 → 새 버전 → 배포. **새 URL을 발급하지 마세요.**
5. 원장 계정으로 로그인 테스트. 첫 한 번은 V1→V2 전환 때문에 느릴 수 있습니다. 두 번째 로그인과 다른 교사 테스트 계정에서 응답시간을 비교합니다.
6. 교사 계정에서 급여메뉴·서버 급여 호출을 거부하는지 검사합니다. 원장 급여 초안 조회만 시험하고 실제 급여 확정은 업무 확인 후 수행합니다.

### 오류 시
- GitHub만 되돌려도 **V2로 전환된 계정은 기존 Google 화면으로 계속 로그인 가능**하도록 V1 verifier를 보존했습니다. 다만 새 OTP 등록 계정은 native-KDF 적용 HTML을 사용해야 합니다.
- Google 배포를 이전 버전으로 되돌릴 때 새로운 V2 계정은 구버전 서버에서 로그인할 수 없습니다. **복구 계획에는 V29 서버 파일과 기존 V1 인증 기록 보존을 포함**해야 합니다. 설정값을 함부로 삭제하지 마세요.
- 실제 HTTP 302/CORS, Google 서비스 장애와 계정별 권한 오류는 코드 가속만으로 제거되지 않습니다.
