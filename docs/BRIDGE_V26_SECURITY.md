# Bridge Wonder V26 보안·등록 정확성 보완

## 적용 범위

기존 직원용 Apps Script에서 확인한 접근권한·동시 요청·중복 수납 기록 문제와 공개 등록 화면의 계약 사본 불일치를 수정했다. 기존 시트 자료와 계정은 유지하며, 수납 대장의 중복 방지 키만 열을 추가해 저장한다. 급여 메뉴는 서버 권한표에서도 원장만 조회·입력할 수 있다.

| 확인한 문제 | 수정한 처리 |
| --- | --- |
| 공개 호출 가능한 백업 함수가 인증 없이 Drive·시트를 변경 | 실제 작업을 비공개 `bw19DailyBackupCheck_`로 이동. 예전 이름의 함수는 활성 Google 계정이 설정된 원장인지 먼저 확인한다. |
| 권한 설정을 읽지 못하거나 형식이 잘못된 경우 역할 기본 권한으로 복귀 | 별도 설정이 없는 경우에만 역할 기본값 사용. 저장소 오류·잘못된 JSON·누락된 배열·알 수 없는 메뉴·조회 권한 없는 쓰기 설정은 역할상 허용된 홈 접근만 남기고 다른 권한을 거부한다. |
| OTP 검증·실패 횟수 증가·사용 완료 처리가 별도 요청에서 겹침 | 같은 ScriptLock 안에서 현재 코드를 다시 읽고 검증·실패 횟수 갱신·소비까지 처리한다. 코드 자체에 만료시각과 실패 횟수를 함께 저장하며, 비밀키 초기화는 잠금 전에 수행한다. 발급도 잠금 획득 후 제한 상태를 다시 확인한다. |
| 문서센터를 통해 권한이 회수된 원본 업무의 정보 조회 가능 | 문서 종류별 원본 조회 권한을 공통 함수에서 확인한다. 종류 목록·원본 목록·미리보기·생성·기존 문서 다운로드·발송·이력에 같은 기준을 적용한다. |
| 수납 대장 저장 뒤 감사기록 오류가 발생하면 재시도 시 중복 저장 | 클라이언트 작업 ID와 수납 내용을 하나의 행으로 기록한다. 같은 ID·같은 내용의 재요청은 기존 저장 결과를 반환하며, 다른 내용의 ID 재사용은 거부한다. 감사기록만 실패한 경우 수납 저장 성공과 별도 경고를 반환한다. |
| 등록 후 수강반을 바꾸면 기존 접수·서명에 새 수강조건이 출력 | 제출 시 수강조건을 깊은 복사로 보관하고 개인 보관용 확인서는 그 사본에서 출력한다. 제출한 요청이 있는 동안 요일·시간·초대 코드 변경과 두 번째 제출을 막고 기존 접수 상태 확인을 제공한다. |
| 개별 등록 코드에서 동의 버전 검증 실패 후 잘못된 조건이 남음 | 조건·동의 버전 표시가 실패하면 조건을 비우고 서명 양식을 숨긴다. 해당 상태에서는 제출할 수 없다. |

홈 접근을 남기는 것은 로그인 후 기본 업무 화면을 제공하기 위한 기존 정책을 따른다. 홈의 반 수 집계 등 기존 표시 전체를 없애는 변경은 포함하지 않는다.

## 문서 종류와 필요한 원본 권한

문서센터 자체의 조회·입력 권한 및 기존 역할 제한에 아래 원본 조회 권한을 추가로 요구한다. 교사는 담당 반 제한도 계속 적용받는다.

| 문서 | 필요한 원본 조회 권한 |
| --- | --- |
| 상담 접수 확인서 | 상담 접수 |
| 수강 등록 확인서 | 수강 신청 확인 |
| 납부 내역 안내서 | 수강 신청 확인, 수납·환불 기록 |
| 수업 안내문 | 수업 시간표 |
| 전자서명 계약서 원본 사본 | 수강 신청 확인 |
| 일반 안내문 | 별도의 원본 자료 없음. 기존 원장·관리자 역할 제한 유지 |

## 설치 시 반영할 사항

1. 직원용 Apps Script의 `Code.gs`와 생성된 `Admin.html`을 함께 갱신한다. 공개 상담·등록 접수용 Apps Script에 직원 서버 코드를 붙여 넣지 않는다.
2. 원장 Google 계정으로 Apps Script 편집기에서 `setupStaffDocumentsV19()`를 한 번 실행한다. 새 비공개 백업 핸들러가 없으면 생성하고, 예전 `bw19DailyBackupCheck` 이름을 사용하는 트리거만 삭제한다. 다른 트리거는 유지한다. 새 함수 이름의 트리거가 이미 있으면 중복 생성하지 않는다.
3. 수납 기록은 처음 새 방식으로 저장할 때 `작업 ID` 열을 자동 추가한다. 기존 첫 7개 열을 확인하고, 별도 사용자 열이 있으면 그 뒤에 붙인다. 기존 행은 다시 쓰지 않는다. 열 구성이 다르거나 작업 ID 열이 중복된 경우 자료를 변경하지 않고 안내한다.
4. 업그레이드 전에 발급한 OTP에는 새 만료·시도 횟수 정보가 없어 사용할 수 없다. 새 인증번호를 요청하면 된다. 기존 로그인 세션을 일괄 삭제하지 않는다.

### 수납 저장 요청 계약

`staffAppendTuition(token, payload)`는 `payload.operationId`를 필수로 받는다. 클라이언트는 32자리 16진수 ID를 생성하고, 저장 결과가 불확실해 같은 내용을 재시도할 때 **같은 ID**를 유지해야 한다. 다른 기록을 저장할 때는 새 ID를 만든다. 예: `crypto.randomUUID().replace(/-/g, '')`.

- 정상 저장: `{ ok: true, operationId, replayed: false }`
- 동일 요청의 재시도: `{ ok: true, operationId, replayed: true }`
- 수납 저장 후 감사기록만 실패: `{ ok: true, operationId, auditWarning: true, message }`
- 작업 ID 누락 또는 동일 ID에 다른 내용: 추가 저장 없이 오류 반환

이전 화면이 작업 ID 없이 호출하면 서버가 안내 오류를 반환하므로, 서버와 직원 화면을 함께 갱신해야 한다. 환불 상한은 최근 일부 행에 제한하지 않고 해당 대장의 기존 납부·환불 기록 전체로 계산한다.

### 등록 화면의 제출 이후 처리

전송을 시작한 요청은 결과가 불확실하더라도 다른 수강반으로 바꾸거나 새 요청으로 다시 전송하지 않는다. 기존 요청의 접수 상태를 확인한다. 별도의 등록은 이전 요청의 처리 결과를 확인한 후 새 페이지에서 시작한다. 개인 보관용 확인서는 제출 당시의 수강조건·신청 정보·동의·서명 사본을 사용한다.

## 검증

`node tests/security.test.cjs`에서 **21개 회귀 시나리오를 통과**했다. 실제 서버 소스를 VM으로 실행하고, 공개 등록 HTML·JavaScript는 jsdom에서 실행했다.

검증 범위는 정책 형식·저장소 오류 시 접근 거부, 원장 전용 급여 권한, 백업 호출 차단과 트리거 이관, OTP 단일 사용·5회 제한·만료·경합 후 재확인, 문서 원본 권한 및 담당 반 제한, 사용자 추가 열을 보존하는 수납 변경, 중복 요청·변조된 재요청·감사기록 실패·5,000행을 넘는 환불 기록, 제출 당시 계약 조건 출력과 등록 중복 제출 차단이다.

실제 Google 메일 발송, 비공개 Drive·스프레드시트, 운영 계정 로그인 및 공개 접수 서버에 대한 실행 검증은 이 오프라인 검증에 포함하지 않는다. 공개 상담·등록 접수 서버 소스는 이 직원용 서버와 별도이므로 그 서버의 법정 동의·접수 검증 완료를 의미하지 않는다. 기존 개인정보 안내의 미확정 사업자·보유기간 항목은 문안 검토 문서에 별도로 기록했다.
